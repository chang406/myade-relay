# Relay 작업 효율 규약

이 문서는 Relay 개발에서 시간과 토큰 사용을 줄이면서 검증 신뢰도를 유지하기 위한 기본 작업 규약이다. `AGENTS.md`의 안전 및 상태 의미 규칙이 항상 이 문서보다 우선한다.

## 1. 기본 작업 단위

- 한 사용자 요청에서는 원칙적으로 하나의 마일스톤만 완료한다.
- 마일스톤은 구현, 관련 테스트, 필요한 문서 갱신, 커밋까지 포함하는 독립 단위다.
- 현재 마일스톤이 끝나면 다음 HANDOFF 항목을 자동으로 시작하지 않고 결과와 다음 후보를 먼저 보고한다.
- 사용자가 “계속 진행”, “끝까지 진행”처럼 명시한 경우에만 여러 마일스톤을 연속 수행한다.
- 범위가 커지거나 새 데이터 형식·외부 권한·실제 provider 조작이 필요해지면 진행 전에 경계를 알린다.

## 2. 시간 기준과 체크포인트

- 일반 코드 작업은 10분 안에 첫 유효 결과를 만드는 것을 목표로 한다.
- 10분을 넘기면 현재까지 확인한 사실, 막힌 지점, 남은 최소 작업을 짧게 보고한다.
- 같은 오류가 두 번 발생하면 같은 방식의 세 번째 시도를 하지 않는 `AGENTS.md` 규칙을 따른다.
- 동일한 접근뿐 아니라 서로 연관된 오류와 재시도가 합산 3회에 이르러 원인 규명 없이 탐색이 반복되기 시작하면, 파일·프로세스·저장 상태가 일관된 안전한 맥락 경계에서 즉시 작업을 멈춘다. 이어 시도한 내용, 확인된 증거, 현재 추정과 대안을 사용자에게 보고하고 추가 지시를 기다린다.
- 실제 CLI 응답이나 사용자 permission을 기다리는 시간은 구현 시간과 분리해 보고한다.
- 예상 20분 이상인 작업은 시작 전에 자동 테스트 단계와 실제 통합 검증 단계를 나눈다.

## 3. 조사와 파일 읽기

- 세션 시작 시 필수 문서와 Git 상태를 확인하되, 이후에는 관련 파일과 필요한 구간만 읽는다.
- 전체 파일 재출력보다 `rg`, `Select-String` 또는 범위 제한 읽기를 우선한다.
- 같은 문서나 로그를 반복해서 읽지 않도록 이미 확인한 사실을 작업 중 기준으로 유지한다.
- 긴 로그는 실패 원인과 상태 전이에 필요한 부분만 출력한다.
- 공식 문서 조사가 필요한 경우 질문을 먼저 좁히고, 구현 결정에 직접 필요한 자료만 확인한다.

## 4. 구현과 테스트

- 먼저 가장 작은 변경과 해당 변경을 증명하는 관련 테스트를 실행한다.
- 개발 중에는 관련 테스트를 우선하고, 전체 `npm test`는 커밋 직전에 한 번 실행한다.
- 상태 모델, ownership, 저장 형식처럼 영향 범위가 넓은 변경은 호환성 테스트를 포함한다.
- 실제 provider 동작을 자동 테스트 결과로 대신하지 않는다.
- 포맷 검사와 Git diff 검토는 커밋 직전에 묶어서 실행한다.
- 실패 원인을 모르는 상태에서 넓은 리팩터링이나 패키지 추가를 하지 않는다.

## 5. 실제 Claude/Codex 통합 검증

- 실제 provider 검증은 코드 변경마다 반복하지 않고 관련 변경을 묶어 한 번 수행한다.
- 자동 테스트가 먼저 통과한 뒤 실제 세션을 연다.
- 검증 전 성공 조건을 exchange ID와 기대 상태로 명확히 정한다.
- permission, workspace trust, development Channel 확인은 사용자가 provider 화면에서 직접 처리한다.
- 대기 중에는 상태 API만 필요한 간격으로 조회하며 과도한 polling을 하지 않는다.
- `delivery_attempted`, `accepted`, `replied`, `delivered`를 서로 대체하지 않고 실제 관찰 상태만 기록한다.

## 6. 문서와 커밋

- 작업 도중 문서를 반복 수정하지 않고 구현과 검증 결과가 확정된 뒤 한 번 갱신한다.
- 실제 검증, 자동 테스트만 한 항목, 미검증 항목을 분리해서 기록한다.
- 한 마일스톤은 가능한 한 하나의 의미 있는 커밋으로 만든다.
- 사용자나 외부 CLI가 만든 관련 없는 파일은 보존하고 커밋 대상에서 제외한다.
- 커밋 후에는 `git status --short`로 남은 사용자 변경을 확인한다.

## 7. 기본 실행 모드

별도 지시가 없으면 `빠른 구현 모드`를 사용한다.

### 빠른 구현 모드

1. HANDOFF의 첫 미완료 항목에서 가장 작은 마일스톤을 선택한다.
2. 관련 코드와 테스트만 수정한다.
3. 관련 테스트 후 전체 `npm test`를 한 번 실행한다.
4. 필요한 문서를 한 번 갱신하고 커밋한다.
5. 실제 provider 검증이 필요하면 자동으로 시작하지 않고 별도 단계로 보고한다.

### 통합 검증 모드

다음 중 하나일 때만 사용한다.

- 사용자가 실제 Claude/Codex 검증을 명시적으로 요청했다.
- provider lifecycle 또는 delivery transport 변경으로 실제 검증 없이는 완료 조건을 충족할 수 없다.
- HANDOFF에 실제 검증이 현재 마일스톤의 명시적 완료 조건으로 적혀 있다.

통합 검증 모드에서도 자동 permission 승인, 터미널 키 입력 주입, 사용자 데이터 삭제는 하지 않는다.

## 8. 완료 보고 형식

완료 보고는 다음 네 항목만 간결하게 포함한다.

1. 변경한 것
2. 실행한 검증과 결과
3. 아직 검증하지 않은 것
4. 다음 한 개의 권장 마일스톤

여러 선택지를 길게 나열하지 않는다. 사용자가 요청하면 그때 전체 로드맵과 예상 시간을 제공한다.
