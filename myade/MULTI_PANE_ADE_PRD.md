# 개인 ADE(myade) — 멀티 pane 터미널 + 페르소나 컴패니언 MVP

> **선행 문서**: 1단계 배경은 [`ADE PROJECT.md`](./ADE%20PROJECT.md), 페르소나 레이어는 [`PERSONA_LAYER_PRD.md`](./PERSONA_LAYER_PRD.md), 현재 상태는 [`README.md`](./README.md)/[`CLAUDE.md`](./CLAUDE.md) 참고.

## 배경

기존 2단계(`myade-gui`, 좌:터미널/우:작업 계획 채팅 구조)는 실사용 패턴과 맞지 않아 이 라운드에서 방향을 전환한다. 목표는 "여러 cmd 창을 사람이 직접 열고 서버로 느슨하게 연결하는" 지금의 1단계 구조를, **하나의 앱 안에 여러 pane이 실제로 내장된 멀티 pane 터미널**로 바꾸는 것이다. 렌더러는 자체 GPU 구현 대신, 검증된 `xterm.js` + 기존 `portable-pty` 조합을 채택한다 — 이번 프로젝트의 차별점은 렌더링이 아니라 페르소나/오케스트레이션 레이어에 있다는 판단에 따른 것이다.

## 이번 단계의 목표 (MVP)

- 하나의 Tauri 앱 안에 여러 개의 실제 셸 PTY가 pane으로 동시에 표시된다 (분할 레이아웃).
- 각 pane에서 `claude` 실행 시, 현재 열린 다른 pane들과 겹치지 않게 캐릭터 페르소나가 자동 배정된다. 필요 시 수동으로 변경 가능하다.
- 앱 안에서 별도 팝업으로 "페르소나 컴패니언 잡담창"을 열 수 있다. 캐릭터 목록에서 골라 그 페르소나 성격만 빌린 독립 대화를 시작한다.
- 기존 1단계 자산(MCP 서버, `pane_list`/`pane_status`, `persona.md`/훅 인프라)을 최대한 재사용한다.

## 확정된 결정 사항

| 항목 | 결정 |
|---|---|
| 기존 `myade-gui`(`src-tauri/`) 코드 처리 | Claude Code가 먼저 코드 재사용 가능성을 평가하고 판단 (아래 "열린 기술 질문" 참고) |
| 레이아웃 | 분할(그리드) 기반 — 여러 pane 동시 표시 |
| 컴패니언 잡담창 | 이번 MVP 범위에 포함 |
| 터미널 렌더링 | `xterm.js` (자체 GPU 렌더러 아님) |
| PTY 관리 | 기존 `portable-pty` 기반, 1개 → N개로 확장 |

## 명시적으로 하지 않을 것 (스코프 아웃)

- **자체 GPU 터미널 렌더러** — 별도 프로젝트로 미룸. 나중에 원하면 렌더링 레이어만 교체 가능하도록 구조를 열어둔다.
- **에이전트 간 자동 협업/작업 위임** (전문 분야별 자동 라우팅) — 이번엔 페르소나 배정과 컴패니언 잡담까지만.
- **git worktree 자동 격리**
- **배포용 설치 파일(.msi 등) 빌드** — 개발 모드(`tauri dev`)로 검증 우선. **다음 단계(Future Scope) 메모: 실제로 배포 빌드를 만들 때는 반드시 코드 서명을 먼저 할 것** — 서명 안 된 `myade-gui.exe`는 Windows Defender 등 여러 백신 엔진에서 `Bearfoos.B!ml`/`Wacatac.H!ml`류 ML 휴리스틱 오탐(트로전/루트킷으로 격리)에 걸리는 걸 실사용 중 직접 확인함 (2026-08-24, VirusTotal에서 Bkav Pro/Cynet/Microsoft 등 다중 엔진 탐지 — lockfile 감사 결과 공급망 침해는 아니고, PTY 스폰+환경변수 조작+headless 프로세스 spawn이 Tauri 앱에서 흔히 겪는 알려진 오탐 패턴으로 확인됨).
- **컴패니언 잡담 세션이 실제 작업 pane의 대화 내용을 아는 것** — 완전히 독립된 대화로 시작 (페르소나 성격만 공유).
- **"지금 포커스된 pane 자동 추적"** — 컴패니언 캐릭터 선택은 사람이 목록에서 직접 고른다.

## 열린 기술 질문 (구현 전 확인 필요)

- 기존 `src-tauri/`의 `pty.rs`, `pane.rs`, `bridge/` 중 이번 구조에 재사용 가능한 부분과 폐기해야 할 부분을 먼저 구분할 것. 참고로 헤드리스 `claude -p` 구동, 승인 큐(`ApprovalQueue`), `run_command`/`write_file` MCP 브릿지는 "오른쪽 채팅이 왼쪽 터미널을 원격 조종"하던 옛 구조 전용이므로 이번엔 불필요할 가능성이 높음 — 각 pane 안에서 `claude`를 평범한 대화형 프로세스로 직접 실행하는 구조이기 때문.
- `SessionStart`/`SessionEnd` 훅(현재 `~/.myade` 전역 스크립트 기반)이, 앱이 내장 PTY 안에서 셸을 띄우는 방식에서도 동일하게 발동하는지 확인 필요. cwd/환경변수가 내장 PTY에서도 기존과 동일하게 전달되는지가 핵심.
- pane별 캐릭터 자동 배정 로직이 "현재 열린 pane 목록"을 어디서 조회할지 — 기존 서버의 `pane_list`를 그대로 쓸지, 앱 내부 상태로 별도 관리할지 결정 필요.
- 컴패니언 잡담창에서 캐릭터를 선택했을 때, 그 캐릭터의 페르소나를 어느 파일에서 읽어올지 — 지금은 전역 `persona.md` 하나뿐이므로, pane별/캐릭터별로 분리할지 여부와 연결됨 (분리하지 않으면 모든 캐릭터가 같은 페르소나 내용을 공유하게 됨 — 이번 MVP에서 허용 가능한지 판단 필요). **(해결됨, 이후 세션에서)**: 처음엔 공용 파일 그대로 두고 MVP를 냈다가, 한 캐릭터 세션의 롤플레이 지시가 전역 선호로 오인 기록되어 다른 캐릭터에게 새는 실제 버그로 이어짐 → 캐릭터별 `persona-<characterId>.md`로 분리. 이후 myade가 myade-gui 전용 사용으로 확정되면서(모든 세션이 항상 캐릭터를 가짐) 공용 파일 자체를 완전히 제거 — 현재 구조는 `CLAUDE.md`의 페르소나 레이어 문단 참고.

## 완료 기준 (Acceptance Criteria)

- [x] 앱 실행 시 최소 2개 이상의 pane을 분할 레이아웃으로 동시에 열 수 있다. (2026-08-23 스크린샷으로 확인: 4-pane 그리드)
- [x] 각 pane에서 실제 셸 명령이 정상 실행되고 출력이 그대로 표시된다 (xterm.js 렌더링 확인).
- [x] 서로 다른 pane에서 각각 `claude`를 실행하면, 겹치지 않는 캐릭터가 자동 배정된다. (실제 배정은 pane 1개(Ari)로 사람이 직접 확인했고, "겹치지 않게"는 `characters::assign`의 유닛테스트로 커버 - 2개 이상의 pane에서 동시에 claude를 띄워 서로 다른 캐릭터가 나오는 것까지 실측하진 않음)
- [x] 컴패니언 잡담창을 열어 캐릭터를 선택하면, 그 페르소나 성격이 반영된 독립 대화가 시작된다. (2026-08-23 사람이 직접 확인)
- [x] 기존 1단계 기능(`pane_list`/`pane_status`, 다른 세션 인지)이 이번 변경으로 회귀하지 않는다. (2026-08-23 회귀 테스트: 순수 launcher로 띄운 세션과 GUI 앱의 pane들이 동시에 `pane_list`에 정상 조회됨)
- [x] 옛 `myade-gui`의 승인 큐/브릿지 관련 코드는 이번 구조에 불필요하면 명시적으로 제거되고, 남기기로 한 부분은 그 이유가 문서화된다. (`bridge.rs`/`poller.rs`/`claude.rs`/`myade-gui/bridge/` 전부 삭제, 남긴 부분 없음 - 자세한 내용은 [`CLAUDE.md`](./CLAUDE.md)와 [`TROUBLESHOOTING.md`](./TROUBLESHOOTING.md) 참고)

## MVP 이후 개선사항

위 "완료 기준"(MVP)과 별개로 이후 진행한 개선 사항들.

- [x] **캐릭터 자동 배정을 셔플백(shuffle bag) 방식으로 교체** (2026-08-24) — 기존엔 로스터를 id
  순으로 정렬해 아직 안 쓰인 첫 캐릭터를 고르는 결정론적 배정이라 항상 같은 순서로만 배정됐다.
  앱 시작 시 로스터를 무작위로 섞은 큐를 만들고, pane 생성마다 그 큐에서 순서대로 하나씩 뽑고,
  큐가 소진되면(로스터를 다 쓰면) 다시 섞어서 계속하는 방식으로 교체했다
  (`myade-gui/src-tauri/src/characters.rs::draw`/`shuffled_queue`, `state.rs`의
  `character_queue`). pane을 닫아도 그 캐릭터는 같은 사이클에서 바로 재사용되지 않으며, 재셔플
  직후 그 캐릭터가 여전히 다른 열린 pane에 배정돼 있다면 건너뛰는 충돌 방지 로직을 포함한다.
  셔플 상태는 세션(앱 프로세스) 한정이며 디스크에 저장하지 않는다 — 재시작하면 새로 섞인다.
  `cargo test --lib` 신규 유닛테스트 5개 통과 + 사용자 직접 확인(4-pane 연속 생성 시 전부 다른
  캐릭터, pane을 닫고 새로 열어도 방금 닫은 캐릭터가 바로 재등장하지 않음, 앱 재시작 시 배정
  순서가 달라짐).
  - **별개의 안정성 이슈 발견**: 위 기능을 검증하던 중, pane을 빠르게 반복 열고 닫으면 이후 pane
    생성 버튼이 무반응해지는 현상을 관찰했다. 셔플백 로직 자체의 버그는 아니며(배정 기능은
    정상 동작 확인됨), 원인 미확인 상태의 별도 이슈로
    [`TROUBLESHOOTING.md`](./TROUBLESHOOTING.md) 11번 항목에 분리해서 기록해뒀다.
- [x] **캐릭터별 색상+아이콘(`CharacterBadge`) 시스템** (2026-08-24) — `~/.myade/characters/*.md`에
  `color`/`icon` 프론트매터 추가(`characters.rs::parse_frontmatter`), `color`가 없으면 id를
  FNV-1a 해시한 HSL→hex로 결정론적 자동 생성(`deterministic_color`, 파일에 리터럴로 기록해둠 —
  ari `#2eb830`/rho `#b89c2e`/momo `#b8952e`/yuki `#70b82e`). `icon`은 `characters_dir()` 기준
  상대경로 이미지를 Rust가 base64 data URI로 변환해 내려준다(`icon_data_uri`,
  `CharacterInfo.iconDataUri`) — 앱 번들 밖 경로를 여는 Tauri asset 프로토콜/capability 설정
  대신 기존 "Rust가 읽어서 JSON으로 반환" 패턴을 그대로 따랐다. 재사용 가능한
  `CharacterBadge.tsx` 컴포넌트(아이콘 있으면 이미지, 없으면 색상 배경+이니셜)로 분리해 pane
  탭 배지에 적용. `cargo test --lib` 프론트매터 파싱/색상 테스트 통과 + 사용자 직접 확인(서로
  다른 색상/이니셜, `color:` 값 손으로 수정 후 반영, 아이콘 연결된 캐릭터는 이미지로 대체).
- [x] **컴패니언 창 캐릭터 선택을 드롭다운으로 교체** (2026-08-24) — 기존엔 캐릭터 이름만 적힌
  pill 버튼이 항상 가로로 늘어서 있었는데(`.companion-roster`), `CharacterDropdown.tsx`(신규,
  `CharacterBadge` 재사용)로 교체했다 — 트리거 버튼(현재 캐릭터 배지+이름)을 누르면 전체
  캐릭터가 배지와 함께 드롭다운으로 펼쳐지고, 고르면 즉시 닫히며 전환된다. 바깥 클릭/Esc로
  닫히고, 전송 중에는 비활성화된다(기존 동작 유지). 사용자 직접 확인 완료.

## 요청사항

먼저 "열린 기술 질문"부터 조사하고, 특히 기존 `src-tauri/` 코드의 재사용 범위를 판단해서 먼저 제안해줘. 스코프에 없는 결정이 필요하면 임의로 정하지 말고 먼저 물어봐줘. 진행하면서 각 단계(레이아웃/PTY 확장 → 캐릭터 자동 배정 → 컴패니언 잡담창)마다 무엇을 만들고 있는지 짧게 설명하면서 진행해줘.
